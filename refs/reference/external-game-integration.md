# Integrating World Forge with External Games

## Purpose

This reference describes the recommended way for an external game project to consume worlds generated by World Forge.

It is written for teams building games in engines such as Godot or Unity, especially:

- full-surface 4X strategy games with an east-west-wrapping world map;
- regional or scenario-based surface campaigns;
- vector-movement fleet-combat games built around planets, moons, stations, belts, and orbital objectives;
- projects that need reproducible procedural worlds without adopting the World Forge desktop application as their runtime.

This document is an architectural direction, not a promise that every interface described here already exists.

As of World Forge `0.3.61`, the repository already separates shared contracts, generator core, generation runtime, renderer, exporters, and the desktop application. The standalone headless executable, game-pack compiler, hosted generation service, and Unity/Godot adapters described below are recommended integration surfaces for future implementation.

## Core principle

World Forge should be treated as a **content authority and compiler**, not as the gameplay renderer or rules engine.

World Forge determines what exists:

- stars, planets, moons, and orbital relationships;
- terrain, elevation, coastlines, rivers, climate, and biomes;
- winds, currents, pressure systems, and other environmental fields;
- stable source coordinates, identifiers, and generation provenance.

The consuming game determines what those facts mean:

- movement cost;
- food, industry, science, or influence yield;
- cover, concealment, and line of sight;
- settlement suitability;
- tactical hazards;
- sensor interference;
- weapon behavior;
- victory conditions.

The preferred flow is therefore:

```text
World Forge source world
        ↓
versioned game-pack compiler
        ↓
game-neutral surface or orbital package
        ↓
consumer-specific adapter
        ↓
native Godot, Unity, or other-engine runtime objects
```

Do not make a game infer authoritative world data from rendered PNGs. Rendered maps and globe textures are useful presentation assets, but the game should consume structured world data.

# Planetary 4X integration

## Primary target: a complete wrappable surface

For a Civilization- or Humankind-style game, the primary gameplay artifact should be a complete global surface grid rather than a collection of disconnected theaters.

The recommended game representation is a conventional cylindrical hex lattice:

```text
World Forge globe
        ↓
global equirectangular projection
        ↓
regular hex grid
        ├── wraps east ↔ west
        ├── bounded north ↔ south
        ├── retains source latitude/longitude
        ├── carries geographic-region membership
        └── supports optional theater subsets
```

This preserves the main advantages expected from a 4X world map:

- units and trade routes can circumnavigate the planet;
- the camera and pathfinder operate on a regular grid;
- borders, zones of control, and city influence remain straightforward;
- the visual board can use familiar hex geometry;
- every gameplay tile can still map back to a position on the generated globe.

### Wrapping contract

The compiled surface grid should make wrapping explicit:

```ts
export type GlobalSurfaceGrid = {
  width: number;
  height: number;
  layout: 'odd-r' | 'even-r';
  wrapX: true;
  wrapY: false;
  cells: SurfaceHexCell[];
  regions: GeographicRegion[];
};
```

The compiler must guarantee correct neighbor relationships across the east-west seam. Depending on the offset-coordinate convention, this may require an even number of columns or another explicit parity rule.

The north and south edges should not wrap. Polar handling is a gameplay and presentation decision. Supported strategies may include:

- compressed polar rows;
- non-settleable polar caps;
- special polar regions;
- omitted extreme-latitude rows;
- impassable ice or ocean edges;
- engine-specific visual caps while retaining bounded gameplay rows.

World Forge should expose enough latitude and climate information for the consumer to choose among these options.

## Game-neutral surface cells

The compiler should export physical and geographic facts rather than ruleset-specific yields.

```ts
export type SurfaceHexCell = {
  id: string;
  q: number;
  r: number;
  latitude: number;
  longitude: number;
  neighbors: string[];

  elevationTier: number;
  relativeElevation: number;
  slopeClass: 'flat' | 'rolling' | 'steep' | 'cliff';

  waterClass:
    | 'land'
    | 'river'
    | 'lake'
    | 'coast'
    | 'shallow-sea'
    | 'deep-sea';

  biomeId: string;
  terrainTags: string[];

  freshwaterAccess: number;
  soilFertility: number;
  forestDensity: number;
  roughness: number;
  visibility: number;
  habitability: number;

  riverEdges: number[];
  cliffEdges: number[];
  coastEdges: number[];

  resourcePotential: Record<string, number>;
  featureIds: string[];
  regionId: string;
};
```

A game adapter may then convert those facts into its own rules:

```text
soilFertility = 0.74
forestDensity = 0.58
roughness = 0.31
freshwaterAccess = 1.00
```

could become food, production, cover, movement, district, or settlement modifiers depending on the consumer.

World Forge should not hard-code one game's yield model into the neutral package.

## Geographic regions

A full-surface 4X map benefits from a region graph in addition to individual hexes.

Regions may be derived from:

- watersheds;
- mountain barriers;
- coastlines;
- island membership;
- river valleys;
- biome transitions;
- accessibility;
- target size and shape constraints.

```ts
export type GeographicRegion = {
  id: string;
  cellIds: string[];
  neighbors: string[];

  dominantBiomeId: string;
  watershedIds: string[];
  coastal: boolean;
  island: boolean;

  settlementSuitability: number;
  agriculturalPotential: number;
  mineralPotential: number;
  strategicConnectivity: number;
};
```

The same region graph can support:

- territory claims;
- settlement placement;
- migration;
- trade;
- culture spread;
- political borders;
- naming;
- scenario generation;
- civilization simulation.

## Theaters remain useful, but secondary

A theater is an optional subset of the global grid, not a separately generated replacement for the planet.

```ts
export type SurfaceTheater = {
  id: string;
  sourcePlanetId: string;
  globalHexIds: string[];
  wrapBehavior: 'inherit-global' | 'bounded';
};
```

Theaters are useful for:

- limited campaigns;
- tutorials;
- scenario maps;
- AI partitioning;
- streaming and memory management;
- previews;
- tactical zoom-ins;
- editor workflows.

A full campaign may use the complete surface while selected scenarios use bounded theater subsets.

# Fleet-combat integration

## Compile local battle spaces, not real-scale star systems

A vector-movement fleet-combat game should not attempt to play directly on a realistically scaled solar system. Real orbital distances produce a mostly empty and tactically unreadable board.

Instead, compile a local battle space around a meaningful engagement context:

- a planet or moon;
- a station complex;
- an asteroid cluster;
- a ring system;
- a Lagrange region;
- a convoy route;
- a jump or transit point;
- a deep-space interception.

```text
Canonical generated system
        ↓
select engagement origin and epoch
        ↓
resolve local orbital context
        ↓
normalize distance and time scales
        ↓
place bodies, hazards, objectives, and approach vectors
```

## Orbital battle package

```ts
export type OrbitalBattlefield = {
  id: string;
  sourceSystemId: string;
  epochDays: number;

  origin: {
    kind: 'body' | 'lagrange-point' | 'station' | 'route' | 'deep-space';
    sourceId?: string;
  };

  scale: {
    kilometersPerGameUnit: number;
    timeSecondsPerTurn: number;
  };

  referencePlane: {
    normal: [number, number, number];
    ascendingNodeRadians: number;
  };

  bodies: TacticalBody[];
  hazards: TacticalHazard[];
  objectives: TacticalObjective[];
  approachVectors: TacticalApproach[];
};
```

World Forge should provide:

- source body identities;
- body radii and masses;
- orbital relationships and epoch positions;
- relative velocities;
- ring, belt, moon, and station context;
- environmental parameters;
- textures and presentation assets.

The consumer determines:

- thrust and vector-movement rules;
- turn duration;
- gravity-assist behavior;
- sensor and weapon modifiers;
- collision consequences;
- objective scoring;
- scenario balance.

## Useful tactical terrain in space

Generated system features can become gameplay terrain rather than decoration:

- planets and moons provide occlusion, sensor shadows, gravity zones, and blockade objectives;
- rings and asteroid fields provide concealment, collision risk, sensor clutter, or movement constraints;
- stations and Lagrange regions provide defensible infrastructure and scenario objectives;
- magnetospheres, stellar radiation, eclipses, and atmospheric boundaries can provide shallow environmental modifiers;
- stable source IDs allow surface regions and orbital objectives to participate in a shared campaign.

The tactical representation may be physically informed without claiming literal astronomical scale.

# Recommended integration architecture

## Preferred approach: a bundled local headless engine

The recommended primary integration is a versioned standalone World Forge engine executable distributed with the consuming game.

```text
world-forge-engine.exe   # Windows
world-forge-engine       # Linux/macOS
```

The executable should contain:

- shared generation contracts;
- generator core;
- generation runtime and workflows;
- `.wforge` serialization;
- game-pack compilation;
- optional preview rendering;
- progress and diagnostics output.

It should not require:

- React;
- the World Forge desktop workspace;
- Firebase authentication;
- browser UI state;
- Tauri-specific presentation logic.

The existing repository structure already supports this direction conceptually:

```text
packages/
  shared/
  generator-core/
  generation-runtime/
  renderer/
  exporters/

apps/
  desktop/
```

A future extraction may add:

```text
packages/
  game-pack-compiler/
  headless-engine/

apps/
  engine-cli/
```

All deployment modes should call the same headless application API.

## Why a subprocess boundary works well

A local process avoids coupling the consumer to TypeScript or JavaScript.

Godot, Unity, command-line tools, CI, and editor plugins can all use the same language-neutral protocol.

For normal one-job-at-a-time generation, standard input and JSON Lines output are preferable to a local HTTP server:

- no port management;
- no firewall prompt;
- no accidentally exposed local endpoint;
- simple cancellation by terminating the child process;
- clear per-job logs;
- straightforward use from C#, GDScript, shell scripts, and CI.

## Example generation request

```json
{
  "protocolVersion": 1,
  "operation": "generate-game-pack",
  "engineVersion": "0.4.0",
  "workflowId": "core.performance-foundation",
  "seed": "campaign-74291",
  "presetId": "earthlike",
  "resolution": {
    "width": 2048,
    "height": 1024
  },
  "gamePack": {
    "kind": "global-surface-4x",
    "hexWidth": 180,
    "hexHeight": 90,
    "wrapX": true
  },
  "outputPath": "./generated/campaign-74291"
}
```

## Example JSON Lines response

```jsonl
{"type":"accepted","jobId":"job-184"}
{"type":"progress","stage":"foundation","progress":0.31}
{"type":"progress","stage":"history","progress":0.72}
{"type":"artifact","kind":"wforge","path":"campaign-74291.wforge"}
{"type":"artifact","kind":"game-pack","path":"campaign-74291.gamepack"}
{"type":"complete","durationMs":67140}
```

The protocol should also define:

- structured errors;
- cancellation;
- engine capability discovery;
- supported workflow and game-pack versions;
- checksums;
- optional preview artifacts;
- deterministic provenance.

## Persistent local daemon: later

An editor or development tool may eventually benefit from a persistent process:

```text
world-forge-engine serve
```

That process could expose JSON-RPC, named pipes, WebSocket, or local HTTP for repeated previews and lower startup overhead.

It should remain a wrapper around the same headless engine API, not a separate generator implementation.

# Hosted generation service

A hosted service makes sense as an additional deployment, not as the only supported way to generate worlds.

```text
Game or browser client
        ↓
World Forge API
        ↓
job queue
        ↓
same headless engine
        ↓
object storage
        ↓
.wforge and game-pack download
```

## Good uses for a hosted service

- browser-based consumers;
- mobile clients;
- multiplayer world-authority workflows;
- very high-resolution jobs;
- queued background generation;
- community world sharing;
- hosted mod or workflow packs;
- premium or credit-metered generation.

## Why it should not be the only path

A cloud-only dependency would mean:

- no offline generation;
- permanent hosting and CPU costs;
- authentication and queue complexity;
- network and service-availability risk;
- weaker long-term durability for purchased games;
- harder local modding and automated testing.

Desktop games should be able to generate and load worlds without depending on the continued operation of a remote service.

The hosted service should accept explicit engine and contract versions so remote generation remains reproducible:

```json
{
  "engineVersion": "0.4.3",
  "workflowId": "core.performance-foundation",
  "gamePackVersion": 2
}
```

A request should not silently run against whichever generator version happens to be deployed that day.

# Rendering responsibility

World Forge should generate data and reusable assets. The consuming engine should render the actual game.

## World Forge may provide

- neutral gameplay data;
- height, biome, water, climate, and region masks;
- globe albedo and analytical textures;
- minimaps and preview images;
- stable source coordinates;
- feature and resource records;
- orbital snapshots;
- battle-space definitions;
- provenance and diagnostics.

## The consuming game should provide

- hex meshes and terrain chunks;
- runtime materials;
- unit navigation;
- cities, roads, districts, and improvements;
- fog of war;
- selection and targeting overlays;
- ships, movement vectors, weapons, sensors, and effects;
- camera and UI behavior;
- simulation and rules.

For a globe, World Forge can export albedo, height, water, biome, climate, and region textures. Godot or Unity should construct the sphere, lighting, atmosphere, clouds, selection layers, and gameplay markers.

For a full-surface 4X board, World Forge should export the global hex lattice and source data. The game should build the native wrapped board.

For fleet combat, World Forge should export the system snapshot and normalized battle package. The game should render ships and tactical effects.

# Versioning and updates

## Pin the engine to the game build

A consuming game should ship with a tested World Forge engine version:

```text
MyGame 0.8.0
  └── World Forge Engine 0.4.3
```

Do not allow the bundled engine to independently auto-update in player installations.

An uncoordinated generator update could:

- change output fields;
- alter world balance;
- break an importer;
- change the result of an existing seed;
- invalidate tutorials, scenarios, or multiplayer assumptions.

The game developer should deliberately update the pinned engine, run compatibility tests, and ship the new engine with a game update.

## Generated worlds are stored artifacts

A game should store or reference the compiled game pack. It should not regenerate the world on every load.

Campaign metadata should retain exact provenance:

```json
{
  "worldForge": {
    "engineVersion": "0.4.3",
    "sourceCommit": "<commit-sha>",
    "workflowId": "core.performance-foundation",
    "workflowVersion": 7,
    "gamePackVersion": 2,
    "seed": "campaign-74291"
  }
}
```

Updating the generator affects new worlds unless the user explicitly requests a migration or rebuild.

## Consumer-project update workflow

A consumer repository may maintain:

```text
tools/world-forge/
  engine-version.json
  download-engine.ps1
  download-engine.sh
  checksums.json
```

Its CI should:

1. download the pinned engine release;
2. verify checksums;
3. generate fixed golden worlds;
4. compile representative game packs;
5. import them through the consumer adapter;
6. verify schemas, wrapping, regions, pathfinding, and expected features;
7. reject incompatible upgrades.

This keeps one authoritative generator codebase without copying World Forge source into every game repository.

# Unity and Godot integration

## Unity

A Unity adapter can:

- launch the engine with `System.Diagnostics.Process`;
- send the job request through standard input;
- parse JSON Lines progress events asynchronously;
- import the resulting package into C# data structures;
- build native terrain, textures, meshes, and ScriptableObjects;
- terminate the child process to cancel generation.

The adapter should remain thin. It should not reimplement generation logic.

## Godot

A Godot adapter can:

- launch the engine through the operating-system process APIs;
- use GDScript or C# to manage the job protocol;
- stream progress into the UI;
- import the package into Resources or custom data objects;
- build native tilemaps, meshes, textures, and orbital scenes.

Again, the adapter should translate contracts and manage process lifetime rather than reproducing World Forge algorithms.

## Console, mobile, and restricted platforms

Some platforms do not permit arbitrary child processes. Those targets may eventually require:

- WebAssembly;
- a native shared library;
- a platform service;
- pre-generated packages;
- remote generation.

Those deployment forms should be implemented only after the headless contracts are stable. A premature port to C#, C++, GDScript, or another language risks creating multiple generators that gradually disagree.

# Game-pack organization

A neutral external package may use a structure similar to:

```text
my-world.gamepack/
  manifest.json

  source/
    provenance.json

  planetary/
    planet.json
    global-hexes.bin
    regions.json
    region-membership.bin

  textures/
    albedo.png
    height.png
    water-mask.png
    biome-mask.png
    region-mask.png

  theaters/
    scenario-northwest/
      manifest.json
      global-hex-ids.bin

  system/
    bodies.json
    orbit-graph.json

  battles/
    planet-03-orbit/
      battlefield.json
      backdrop.png
```

The game-pack format should be versioned separately from `.wforge`:

```json
{
  "format": "world-forge-game-pack",
  "formatVersion": 1,
  "sourceWforgeVersion": 3,
  "compilerVersion": "0.1.0",
  "rulesetAdapter": "neutral"
}
```

Binary arrays are appropriate for large cell and raster data, while JSON remains useful for manifests, IDs, relationships, and human-readable metadata.

# Recommended delivery sequence

## 1. Stable headless application API

Extract an API that can generate, load, save, validate, and compile worlds without importing the desktop UI.

## 2. Command-line engine

Add a standalone executable with:

- JSON job input;
- JSON Lines progress output;
- cancellation;
- structured errors;
- exact provenance;
- deterministic artifact locations.

## 3. Neutral game-pack compiler

Define:

- manifest and versioning;
- global surface grid;
- geographic region graph;
- stable IDs;
- compressed arrays;
- orbital battle packages;
- preview assets.

## 4. Full-surface 4X compiler

Build:

- east-west-wrapping global hex projection;
- seam-safe adjacency;
- polar treatment options;
- terrain aggregation;
- river, coast, and cliff edges;
- region membership;
- neutral resource and settlement potential.

## 5. Reference consumer adapters

Build one thin Godot or Unity importer first, then use the same protocol and package contract for the other engine.

## 6. Fleet-battle compiler

Build:

- engagement-origin selection;
- epoch snapshots;
- local plane projection;
- normalized tactical scale;
- body, hazard, objective, and approach placement.

## 7. Optional hosted service

Deploy the same headless engine behind a versioned API, job queue, and artifact store.

## 8. Alternative runtime targets

Evaluate persistent local daemon, WebAssembly, and native-library packaging only where a target platform requires them.

# Decisions

The recommended external-consumption architecture is:

1. The primary planetary 4X artifact is a complete east-west-wrapping global hex surface.
2. Theaters are optional subsets, scenarios, and operational partitions of that global grid.
3. World Forge remains the content authority and game-pack compiler; consumer projects own gameplay rules and runtime rendering.
4. The primary integration surface is a bundled, versioned local headless executable.
5. Godot, Unity, CI, and editor tools communicate with that executable through a language-neutral job protocol.
6. The game pins and ships a tested engine version; the bundled engine does not auto-update independently.
7. Generated packages and exact provenance are retained in campaign saves.
8. A hosted service runs the same headless engine and remains optional rather than mandatory.
9. Direct source embedding or a second-language generator port is deferred until stable contracts and platform requirements justify it.
10. Full-surface 4X and local orbital battle spaces are separate projections of the same canonical generated world and stable identity system.

# Current-status boundary

This document defines the intended external architecture.

It does not claim that World Forge `0.3.61` currently ships:

- a standalone engine executable;
- a stable external job protocol;
- a game-pack compiler;
- a global hex compiler;
- a hosted generation API;
- official Unity or Godot adapters.

External projects should treat current `.wforge`, JSON, binary, and image exports as evolving preview formats until dedicated external contracts are versioned and published.

Before embedding, redistributing, or modifying World Forge code or engine binaries, review the repository license and any applicable commercial licensing terms. This reference is technical guidance, not legal advice.
